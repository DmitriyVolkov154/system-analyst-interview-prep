# API, REST, SOAP и интеграции

## API
API — интерфейс, через который одна система взаимодействует с другой по определённому контракту.

API не равно SQL-запрос. SQL работает с БД, а API задаёт внешний способ взаимодействия с системой.

## REST
REST — архитектурный стиль. На практике REST API часто работает поверх HTTP.

Типичные HTTP-методы:
- GET — получение данных;
- POST — создание/выполнение операции;
- PUT — полная замена ресурса;
- PATCH — частичное изменение;
- DELETE — удаление.

Для аналитика важно уметь описать:
- endpoint;
- HTTP method;
- параметры/path/query;
- headers;
- авторизацию;
- request body;
- response;
- коды ответа;
- ошибки;
- ограничения и бизнес-правила.

## SOAP
SOAP — протокол обмена сообщениями, обычно с XML и формальным контрактом WSDL.

Не считать любой XML автоматически SOAP. XML может быть просто форматом сообщения в интеграционной шине.

## Шина / message broker
Шина или брокер — инфраструктура обмена сообщениями.

Синхронный API часто выглядит как request → response.
Асинхронная интеграция может выглядеть как producer → message/broker → consumer.

Система может одновременно использовать API и шину.

## Не каждая интеграция требует API
Варианты:
- REST/HTTP;
- SOAP;
- message broker / шина;
- файлы CSV/XML/другие форматы;
- DB-level integration;
- другие специализированные механизмы.

Способ выбирается архитектурой и ограничениями проекта.

## Что описывать в интеграции
- source system;
- target system;
- инициирующее событие;
- бизнес-назначение;
- структура сообщения;
- обязательные/необязательные поля;
- mapping;
- правила обработки;
- ошибки;
- retries;
- дубликаты/idempotency при необходимости;
- статусы;
- acknowledgement/response, если есть.

## Реальный рабочий пример
Система уровня 4 формирует XML-сообщение с нужными данными и передаёт его через шину системе уровня 3. Принимающая система разбирает сообщение и записывает необходимые данные в свою БД.

Нельзя автоматически называть это SOAP: для этого нужно знать, используется ли SOAP envelope/WSDL и соответствующий протокол взаимодействия.

## Правильная роль аналитика
Аналитик описывает бизнес-потребность, данные, правила и контракт взаимодействия. Конкретный технический механизм прорабатывается с разработчиком/архитектором, но аналитик должен понимать выбранный способ настолько, чтобы корректно зафиксировать интеграцию.
